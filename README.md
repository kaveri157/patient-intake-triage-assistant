# Transaction Risk Investigation Assistant

A fraud-desk investigation assistant. Given a single customer's transaction
history, it runs a deterministic rule engine to decide whether anything
needs a human investigator's attention, then asks Gemini to turn the
engine's findings into a plain-language report — never the other way
around. The LLM never sees raw, unstructured freedom to invent a
transaction or a verdict; it only narrates what the rule engine already
found, and it is explicitly instructed to never claim fraud has occurred.

## Why it's built this way

- **Deterministic logic decides, the LLM explains.** `src/rules.py` computes
  every finding (large transfers, new-payee bursts, odd-hours activity,
  pattern breaks vs. the customer's own baseline) from the raw transaction
  data alone — no LLM call involved. That JSON is the *only* input the LLM
  ever sees (`src/gemini_client.py`), so every claim in the narrative is
  traceable back to a specific transaction ID.
- **A clean case comes back clean.** If no rule fires, the report says so
  plainly instead of manufacturing concern (see `CUST-1001`).
- **Graceful degradation.** If `GEMINI_API_KEY` is missing or the API call
  fails for any reason, the app falls back to a deterministic narrative
  template instead of crashing or hanging — the investigation report is
  always produced end-to-end. The response includes `narrative_source` so
  you can see which path was used.
- **Never over-claims.** The system flags and explains; it explicitly never
  states that fraud occurred — that judgement is left to the investigator,
  per the problem statement.

## How to run

```bash
pip install -r requirements.txt
python app.py
```

Then open http://localhost:8000. Set `GEMINI_API_KEY` in your environment
to get LLM-written narratives; without it, the app still runs fully using
the template fallback described above.

## Data

No external dataset is used. `data/customers.json` contains 5 synthetic
customers generated by `src/data_gen.py` (deterministic, seeded):

- `CUST-1001` — entirely routine history → comes back clean
- `CUST-1002` — one atypically large transfer
- `CUST-1003` — a burst of payments to a newly-added payee
- `CUST-1004` — odd-hours (1am–4am) ATM activity
- `CUST-1005` — multiple stacked signals (large transfer + pattern break)

Regenerate at any time with `python -m src.data_gen` from the repo root.

## API

- `GET /api/customers` — list available customers
- `GET /api/investigate/<customer_id>` — run the rule engine + narrative for one customer
- `GET /api/health` — liveness check

## What's deliberately left to the human

The system never approves, rejects, or declares fraud. It ranks findings,
cites the transactions and rule behind each one, and states plainly when a
customer's history needs no action — the investigator makes the call.
